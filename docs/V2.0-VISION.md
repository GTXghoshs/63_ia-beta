# 63_ia 2.0 — Visão pública

## Visão

A versão 2.0 será um **ambiente local de desenvolvimento assistido por IA**, inspirado na experiência de ferramentas como Claude Code, mas construído para Linux, com modelos GGUF locais, memória própria, ferramentas locais e personalização controlada pelo usuário responsável.

A unidade principal do produto não será apenas um modelo de linguagem. Será um conjunto coordenado de componentes: interface de trabalho, núcleo de raciocínio, memória, planejador, gateway de ferramentas, terminal, sistema de plugins, auditoria e políticas de execução.

> **Princípio de propriedade:** a IA, os modelos, os arquivos, as ferramentas e as ações executadas pertencem ao ambiente do proprietário. A plataforma não deve apresentar uma ação autônoma como se fosse responsabilidade de um serviço externo; o proprietário configura as permissões, autoriza os níveis de autonomia e responde pelas ações que decidir habilitar.

## O que a versão 2.0 será

Ela funcionará como um **copiloto local de projetos**. A pessoa usuária poderá abrir um diretório de trabalho, conversar com a IA, pedir alterações, revisar um plano, permitir que arquivos sejam criados ou modificados, executar testes e abrir uma prévia local. A IA deverá mostrar o que pretende fazer antes de executar ações relevantes e registrar o resultado depois.

O ambiente será personalizável em quatro dimensões: modelo, identidade, ferramentas e políticas. A pessoa usuária poderá selecionar o modelo GGUF, definir estilo e instruções permanentes, habilitar ou desabilitar ferramentas, criar plugins e estabelecer regras para leitura, escrita, execução, rede e acesso ao Obsidian.

## O que ela não será

A versão 2.0 não deverá ser apresentada como uma consciência artificial, pessoa digital ou entidade independente. Ela será um **sistema de software que coordena um modelo local e ferramentas autorizadas**. Pode possuir personalidade configurável, memória e comportamento consistente, mas isso não comprova consciência, intenção própria ou responsabilidade jurídica independente.

Também não deverá executar comandos arbitrários, modificar o sistema sem registro ou tomar decisões irreversíveis silenciosamente. A autonomia será uma configuração graduada, não um estado padrão.

## Componentes fundamentais

| Componente | Responsabilidade |
|---|---|
| Dashboard | Interface de chat, arquivos, plano, terminal, logs, permissões, modelos e prévia local |
| Mind Core | Orquestra contexto, instruções, memória, planejamento e resposta do modelo |
| Model Runtime | Executa o modelo GGUF localmente pelo llama.cpp/Vulkan |
| Workspace | Representa o projeto aberto, arquivos permitidos, comandos e estado de execução |
| Planner | Divide uma solicitação em etapas, dependências, riscos e critérios de conclusão |
| Tool Gateway | Única porta de acesso a arquivos, terminal, Git, navegador local, Tavily e Obsidian |
| Policy Engine | Decide o que é permitido, o que exige confirmação e o que é bloqueado |
| Memory Layer | Controla memória de trabalho, episódios, conhecimento indexado e procedimentos |
| Verifier | Executa testes, lint, validações, diffs e checagens antes de concluir |
| Audit Log | Registra solicitação, plano, ferramenta, parâmetros, aprovação, resultado e erro |
| Plugin Runtime | Instala e executa extensões com manifesto, escopos e versão compatível |

## Contrato de responsabilidade

Cada ação realizada pela plataforma deverá possuir um responsável operacional identificável: a pessoa usuária que a autorizou ou a política previamente aprovada pelo administrador do ambiente. A interface deverá diferenciar claramente entre **sugestão**, **plano**, **pedido de confirmação**, **ação executada** e **resultado verificado**.

A plataforma não deverá ocultar a origem de uma ação. Quando um arquivo for alterado, o sistema deverá informar qual tarefa, qual ferramenta e qual etapa produziram a mudança. Quando um comando for executado, deverá existir registro de comando, diretório, horário, código de saída e resumo do resultado, sem registrar segredos desnecessariamente.

## Modelo de autonomia

A autonomia será dividida em níveis. O nível zero permite somente conversa e sugestões. O nível um permite leitura de arquivos selecionados. O nível dois permite criar arquivos e executar verificações não destrutivas. O nível três permite editar um workspace autorizado e corrigir falhas de testes. O nível quatro permite automações recorrentes, sempre dentro de políticas explícitas. Ações destrutivas, instalação de pacotes, acesso a credenciais, operações externas e publicação exigirão confirmação separada.

A pessoa usuária poderá interromper uma execução, revogar permissões, encerrar o processo, restaurar arquivos e consultar o histórico. O sistema deverá preferir operações reversíveis, diffs e branches antes de mudanças amplas.

## Direção de produto

A versão 2.0 deverá parecer uma **estação de desenvolvimento local**, não um chatbot decorado. O centro da experiência será o projeto aberto e o ciclo:

> **entender → planejar → aprovar → executar → testar → revisar → registrar**

A IA poderá manter uma identidade configurável, mas a identidade não terá poder para alterar as próprias políticas. O arquivo de identidade, princípios e limites será editável pelo proprietário e protegido contra modificação automática.

## Critério de sucesso

A versão 2.0 será considerada bem-sucedida quando uma pessoa usuária puder solicitar a criação ou evolução de um aplicativo local, acompanhar o plano, revisar mudanças, executar testes, abrir a prévia e recuperar o contexto do projeto em uma nova sessão, sem enviar obrigatoriamente código ou documentos para a nuvem e sem perder visibilidade sobre as ações realizadas.

# Política de responsabilidade e permissões da versão 2.0

## Princípio central

A versão 2.0 deve tratar toda ação como uma decisão operacional do proprietário. O sistema poderá sugerir, planejar e executar conforme as permissões configuradas, mas não deverá esconder que uma ferramenta foi usada ou atribuir a um serviço externo a responsabilidade por uma ação feita na máquina do proprietário.

A interface deverá mostrar uma linha de responsabilidade em cada tarefa: **quem pediu**, **qual política autorizou**, **qual ferramenta executou**, **em qual workspace**, **com qual resultado** e **como desfazer ou interromper**.

## Classes de risco

| Classe | Exemplos | Padrão |
|---|---|---|
| Informativa | Ler arquivo selecionado, listar diretório autorizado, consultar status | Permitida |
| Reversível | Criar arquivo novo, gerar teste, atualizar nota, criar branch | Permitida com registro; confirmação configurável |
| Alteração controlada | Editar arquivo existente, instalar dependência em workspace, executar build | Confirmação no primeiro uso ou por tarefa |
| Sensível | Alterar configuração do sistema, acessar credencial, escrever fora do workspace, enviar consulta externa | Sempre confirmar |
| Destrutiva | Apagar arquivo, resetar Git, matar processos, alterar permissões, remover pacote | Sempre confirmar de forma explícita |
| Irreversível/externa | Publicar, fazer deploy, enviar dados, pagar, enviar mensagem, expor serviço | Bloqueada por padrão e confirmação dupla |

## Escopos

As permissões deverão ser concedidas por escopo, nunca como uma autorização global implícita. Um workspace poderá autorizar leitura e escrita apenas em seu diretório; o vault do Obsidian poderá ser autorizado para leitura, escrita ou ambos; o terminal poderá aceitar somente comandos nomeados; a Tavily poderá ser habilitada apenas para consultas manuais.

```toml
[policy]
mode = "confirm-sensitive"
allow_network = false
allow_external_publish = false

[workspace]
root = "/home/usuario/projetos/meu-app"
read = ["src", "tests", "docs"]
write = ["src", "tests", "docs"]

[tools.terminal]
commands = ["npm test", "npm run lint", "npm run build"]
require_confirmation = true

[tools.tavily]
enabled = false
require_confirmation = true
```

## Confirmação

Uma confirmação válida deverá informar a ação concreta, o caminho afetado, o comando completo ou resumo equivalente, o efeito esperado, o risco e a forma de desfazer. Botões genéricos como “continuar” não são suficientes para ações destrutivas.

A confirmação deverá expirar após um período curto e ser vinculada à tarefa, ferramenta, escopo e parâmetros. Alterar o comando depois da confirmação deverá invalidar a autorização. O usuário poderá aprovar uma ação única, uma etapa, uma tarefa ou um conjunto de operações de baixo risco.

## Auditoria

O log deverá registrar eventos estruturados em JSONL ou SQLite local. Cada evento deverá possuir identificador, tarefa, sessão, horário, workspace, ferramenta, operação, escopo, decisão de política, confirmação, código de saída e resumo. Segredos, tokens, conteúdo completo de arquivos sensíveis e saídas extensas não deverão ser gravados automaticamente.

A interface deverá permitir filtrar por projeto, sessão, ferramenta, risco e resultado. O proprietário deverá conseguir exportar ou apagar o histórico conforme a política local, preservando apenas o que for necessário para depuração e responsabilidade operacional.

## Interrupção e recuperação

Toda execução longa deverá possuir cancelamento. O cancelamento deverá impedir novas chamadas de ferramenta e tentar encerrar processos filhos associados à tarefa. Alterações de arquivos deverão preferir patch, backup ou snapshot. Antes de uma sequência ampla, o sistema deverá oferecer criação de snapshot local ou branch.

Quando uma etapa falhar, a IA deverá parar ou voltar ao modo de planejamento, em vez de continuar indefinidamente. A correção automática deverá ter limite de tentativas e apresentar o diff antes de aplicar mudanças posteriores.

## Acesso remoto

O acesso remoto não deve ampliar as permissões do desktop. O celular poderá iniciar tarefas e acompanhar eventos, mas continuará submetido às mesmas políticas, confirmações, limites e logs. O terminal deverá permanecer desabilitado por padrão no acesso móvel.

O modo remoto deverá usar autenticação independente, sessão expirada, logout, limitação de tentativas e binding protegido. O `llama-server` e ferramentas internas deverão continuar inacessíveis diretamente pela rede.

## Regra de responsabilidade

A mensagem de encerramento de cada tarefa deverá conter uma seção **Responsabilidade operacional**, informando que as ações foram executadas no ambiente local conforme as permissões do proprietário e listando qualquer efeito externo, alteração persistente ou falha não verificada.

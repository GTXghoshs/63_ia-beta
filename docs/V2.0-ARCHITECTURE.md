# Arquitetura proposta da versão 2.0

## Modelo mental do produto

A versão 2.0 deve ser organizada como um **workspace de desenvolvimento assistido**, não como uma chamada direta ao modelo. O usuário abre um projeto, conversa com a IA, acompanha um plano e permite que ferramentas específicas atuem dentro de escopos definidos.

```text
Usuário
  │
  ▼
Dashboard local ── sessão, projeto, chat, plano, diff, logs
  │
  ▼
Mind Core ── contexto, planejamento, memória, decisão de ferramenta
  │
  ├── Model Runtime ── llama.cpp / GGUF / Vulkan
  ├── Memory Layer ── Obsidian / índice semântico / histórico
  ├── Tool Gateway ── arquivos / terminal / Git / Tavily / prévia
  ├── Policy Engine ── permissões / confirmação / bloqueios
  └── Verifier ── testes / lint / build / health check
```

O modelo nunca deverá acessar diretamente o sistema de arquivos ou o terminal. Toda ação deverá passar pelo **Tool Gateway**, que recebe uma intenção estruturada, verifica a política, registra a solicitação e somente então chama a ferramenta correspondente.

## Workspace de projeto

Cada projeto deverá possuir um diretório-raiz explícito, uma configuração própria e um estado de sessão. O workspace poderá conter um arquivo `llama.local.yaml` ou `llama.local.toml` com o modelo, comandos permitidos, diretórios adicionais, comandos de teste e comportamento da prévia.

```text
meu-app/
├── llama.local.toml
├── .llama/
│   ├── sessions/
│   ├── memory/
│   ├── audit/
│   ├── plans/
│   └── snapshots/
├── src/
├── tests/
└── docs/
```

O arquivo do workspace não deverá conter tokens secretos. Credenciais e chaves permanecerão em um armazenamento local separado, com permissões restritas ao usuário.

## Ciclo de uma tarefa

Cada pedido deverá ser convertido em um objeto de tarefa com identificador, objetivo, escopo, plano, permissões necessárias e critérios de conclusão. O ciclo recomendado é:

| Etapa | Estado | Resultado visível |
|---|---|---|
| Entender | `understanding` | Resumo do pedido e dúvidas detectadas |
| Planejar | `planned` | Plano ordenado, arquivos previstos e riscos |
| Autorizar | `awaiting_approval` | Permissões e ações que precisam de confirmação |
| Executar | `running` | Eventos de ferramentas e progresso |
| Verificar | `verifying` | Testes, lint, build e diferenças encontradas |
| Revisar | `review` | Diff, falhas, avisos e proposta de próximos passos |
| Concluir | `completed` | Resumo, arquivos alterados e memória registrada |
| Interromper | `cancelled` | Motivo da interrupção e estado recuperável |

Esse ciclo evita que uma resposta do modelo seja confundida com uma ação já executada. A interface deverá mostrar o estado atual e permitir cancelar antes de cada etapa sensível.

## Ferramentas de primeira classe

A primeira versão do gateway deverá conter ferramentas pequenas e explícitas: leitura de arquivo, busca em arquivos, criação de arquivo, edição por patch, listagem de diretório, execução de testes autorizados, execução de build autorizado, consulta de status do llama.cpp, leitura/escrita de notas Obsidian, pesquisa Tavily e abertura de prévia local.

Cada ferramenta deverá possuir um manifesto com nome, versão, descrição, entradas, efeitos colaterais, escopos exigidos, possibilidade de simulação e política padrão. Uma ferramenta que não tenha manifesto não poderá ser chamada pelo Mind Core.

## Protocolo interno

O Mind Core deverá receber e produzir estruturas validadas, mesmo que a conversa com o usuário seja natural. Um pedido de ferramenta deverá seguir um formato semelhante a:

```json
{
  "tool": "workspace.write_file",
  "reason": "Criar a tela inicial do aplicativo",
  "path": "src/App.tsx",
  "content": "...",
  "risk": "write",
  "requires_approval": true
}
```

O gateway deverá validar o caminho, o tamanho, a extensão, o workspace, a política e o estado da tarefa. O modelo não deverá fornecer uma string livre para um shell geral como substituto de uma chamada de ferramenta.

## Prévia e ciclo de desenvolvimento

A prévia local deverá ser um processo separado do dashboard. O gateway poderá iniciar o comando definido pelo workspace, observar a porta, verificar o health check e informar a URL. O processo deverá ser associado ao identificador da tarefa, possuir timeout e poder ser encerrado pela interface.

O fluxo visual ideal será semelhante a um ambiente de desenvolvimento: árvore de arquivos, chat, plano, diff, terminal de eventos, testes e prévia em painéis coordenados. A IA não deverá esconder o terminal; deverá apresentá-lo como uma sequência de eventos verificáveis.

## Modelos e roteamento

O sistema deverá permitir um modelo principal, um modelo menor para tarefas rápidas e, no futuro, modelos especializados para embeddings ou classificação. O roteador poderá selecionar o modelo, mas deverá mostrar qual modelo foi usado e por quê. A troca de modelo não deverá apagar a memória do projeto.

Para cada GPU compatível, a configuração inicial deverá priorizar modelos GGUF e quantizações que deixem espaço para KV cache. Contexto grande deverá ser tratado por recuperação de memória e medição de capacidade, não por colocar todo o projeto em uma única solicitação.

## Resultado esperado

A arquitetura deve permitir que a pessoa usuária diga “crie este aplicativo”, acompanhe o plano, aprove os arquivos, observe os testes, veja a prévia e recupere o contexto posteriormente. Ao mesmo tempo, deve ser possível explicar cada mudança por meio de tarefa, ferramenta, permissão e log.
